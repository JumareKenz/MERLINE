01 Executive Summary

Status — decisions confirmed

Strategy: Option A, in-place refactor with hard legacy isolation — confirmed. Target hierarchy and the evidence rule (§3, §8) — confirmed. MVP boundary (§15) — confirmed, with its acceptance trace adopted as the primary end-to-end test.

Correction applied: Phase 0 no longer moves or deletes any legacy code. Isolation is achieved by deregistration in place — removing MERL modules from navigation and from application registration, marking them legacy, and enforcing the boundary with an import test — while the schema stays untouched until the data-preservation decision is confirmed. Relocation and deletion happen progressively afterwards. This avoids breaking hidden imports, prisma/seed.ts, and the path-based bind mounts in docker-compose.yml. See §14, Phase 0.

The repository contains a partially-built general MERL platform: a Next.js 14 dashboard, a NestJS 11 API with 19 modules, and a 40-model Prisma schema oriented around projects, studies, logframes, indicators, questionnaires and form submissions. Roughly half of the active product surface is MERL domain that the new direction discards, and none of the qualitative interview pipeline exists.

The good news for the transition is structural. The MERL domain is module-boundaried, not entangled: indicators, logframes, questionnaires and submissions are separate NestJS modules and separate route trees, with very few imports crossing into the generic foundations. Quarantining them is a routing and navigation change, not a refactor. Meanwhile the generic foundations that the qualitative product needs — auth structure, organizations, users, projects, media upload, audit schema, API response conventions, the design system, and a Docker stack that already provisions MinIO and Redis — exist and are reusable in shape.

The catch: every reusable foundation has a defect in it

Reuse here means reusing the skeleton, not the behaviour. Authentication cannot issue a usable token. No list or detail endpoint filters by organization. Both authorization guards are written and never applied — and the permissions table is never populated by any code path, so switching the guard on today would lock every user out of everything. There are no database migrations. Media is written to local disk. The AI gateway invents answers when a provider fails. All confirmed in source

Recommended strategy: Option A — refactor in place, with hard module isolation. The decisive evidence is that there is no data to migrate: no prisma/migrations directory exists, the schema has only ever been applied via db push, and the only seeded content is demo data. A 19-commit repository with no production data and no migration history is cheap to restructure and expensive to recreate — the design system alone is ~190 components, and the Docker/CI scaffolding would take weeks to rebuild. Option B's main benefit (escaping legacy coupling) is largely unavailable to buy, because the coupling is weak.

The plan below is four phases. Phase 1 is non-negotiable and comes before any interview feature. Collecting real interview audio from real participants on a platform with broken auth, no tenant isolation, no migrations and ephemeral storage would create an unrecoverable data-protection incident, not a prototype.

03 Product Direction

Merline becomes a qualitative interview platform for field research. It helps research teams create interview guides, assign interviews, capture consent, record in the field, work offline, upload audio safely, transcribe, review transcripts, generate evidence-linked insights, approve findings, and produce structured reports.

The one principle that governs the architecture

Every AI-generated finding must be traceable to supporting transcript evidence. This is not a feature to add later — it is a schema constraint that must exist from the first migration, because retrofitting provenance onto generated text is effectively impossible. The chain is:

Finding → Quotation → TranscriptSegment → Transcript → Recording → Interview → Project

A finding without supporting evidence must be impossible to approve or publish. Approval and publication are the hard gates: a draft AI proposal may exist transiently while it is being assembled, but it can never acquire an approving ReviewDecision or reach a report without evidence. Enforce with a non-nullable segmentId on Quotation, a transactional check on the approval transition, and a database constraint on published findings — not with UI validation. Every Quotation must carry a segment id plus a start/end offset that can be replayed against the audio.

Strategic consequence for the existing product

The existing platform's centre of gravity — Study with its 22-value MERL type enum, logframes, indicators, questionnaires and submissions — is not the new product's centre of gravity. The new hub is Interview. The correct move is not to extend Study with interview fields; it is to build the interview domain alongside it and let the MERL domain go quiet.

05 Current Architecture Assessment

Coupling — the question that decides the strategy

The critical finding for transition planning is that the MERL domain is loosely coupled to the generic foundations. Each domain lives in its own NestJS module with its own controller, service and DTOs, and its own Next.js route subtree. The couplings that exist are narrow:

  • Study is the hub: questionnaires, assignments, indicators, submissions and reports all FK to it. Confirmed
  • Project → Logframe is a one-to-one that can be dropped without touching Project. Confirmed
  • Media FKs to Submission — but nullably (submissionId String?), so audio can attach elsewhere without a schema fight. Confirmed
  • User carries back-relations to assignments and submissions, which is cosmetic and easily extended.

Practical consequence: the qualitative domain can be built as new modules hanging off Organization → Project without importing a single MERL service. That is what makes refactor-in-place viable.

Sequencing trap — seed before you enforce

Applying PermissionGuard before seeding the permission catalogue and attaching permissions to the seeded roles will return ForbiddenException('Insufficient permissions') for every decorated route, including for the administrator. 13 Recommended Transition Strategy

Option A — refactor in place, with hard module isolation Confirmed

Isolation is a structural requirement, not a naming convention — but it is achieved by deregistration rather than relocation, so that removing code from the application graph and moving it on disk remain two separately-attributable steps. The decision rests on four pieces of evidence from the repository.

  1. There is nothing to migrate. No prisma/migrations directory exists; the schema has only ever been applied with db push; the only seeded content is demo data. Option B's usual advantage — a clean break from legacy data — is not available for purchase because there is no legacy data. Confirmed
  2. The coupling is weak. MERL domains are separate NestJS modules and separate route subtrees. Media.submissionId is nullable; Logframe detaches cleanly from Project. The qualitative domain can be built without importing a single MERL service. Confirmed
  3. The reusable surface is large and expensive to recreate. ~190 frontend components, a consistent API envelope, and a Compose stack that already runs MinIO with an auto-created bucket, Redis, and Mailpit — all of which the qualitative product needs and none of which the code currently uses. Confirmed
  4. Platform defects are shared, not MERL-specific. Broken auth, absent tenancy, unwired guards and missing migrations would have to be fixed in a copied codebase too. Fixing them once in place is strictly cheaper.

The conditions that make this work

Option A degrades into Option C without these. They are not optional:

  • Structural isolation by deregistration, enforced by test. Remove legacy modules from the app.module.ts imports array and from navigation, leaving the files in place. An unregistered module's providers cannot be injected, so the boundary is real without moving anything. Back it with an import-boundary test in CI (§14, Phase 0) that fails the build if qualitative code imports legacy code — and verify the test fails when it should. Relocation and deletion follow progressively in later phases, once the boundary has held.
  • A tenant-scoped base repository. Every new module extends it. Writing an unscoped query should require deliberately bypassing the helper, and a lint rule or test should catch it.
  • No new work on MERL modules. Legacy is frozen: no features, no refactors, bug fixes only if they block the qualitative path.
  • A dated deletion decision. Set a date by which §17's data-preservation question is answered and legacy is deleted, so quarantine does not become permanent.
  • Baseline migration before new models. Generate it in Phase 1, not after the qualitative schema lands.

If the team later concludes the legacy surface is genuinely obstructive, Option B remains available at low cost — having fixed the foundations in place, a copy-forward becomes a mechanical extraction rather than a rescue.

14 Phased Implementation Roadmap

PHASE 0 Repository and product reset No user-facing features

Deregistration, not relocation

Phase 0 does not move or delete a single file. Legacy code stays exactly where it is and keeps compiling; it simply stops being reachable. Physically moving directories in the same step that removes them from the application graph conflates two different risks and makes a failure hard to attribute — and this repository has concrete hidden dependencies that a move would break silently: prisma/seed.ts creates a study and a questionnaire, docker-compose.yml bind-mounts src and prisma by path, and the frontend api-client.ts still declares the full legacy API surface. Relocation happens progressively in Phase 2+, after the boundary has been proven to hold.

Deliverables — in this order

  1. Remove MERL routes from active navigation. Strip the Studies, Questionnaires, Indicators, Submissions, Data Collection and AI Assistant entries from NAV_GROUPS in components/layout/sidebar.tsx. Route files stay on disk and remain directly addressable — useful for reference and for any data-export work.
  2. Remove MERL modules from active application registration. Delete the legacy entries from the imports array in app.module.ts. The module files remain in src/. This is the real isolation boundary: an unregistered module's providers cannot be injected, so a legacy service cannot leak into a qualitative one even by accident.

  5. Preserve the schema untouched. No models removed, no tables dropped, no relations altered until the data-preservation decision is confirmed.

The import-boundary test

This is the mechanism that makes deregistration-in-place as safe as relocation. Assert it in CI so the boundary cannot erode quietly:

  • An ESLint no-restricted-imports rule giving the same feedback in-editor, so violations are caught before CI.
  • A test asserting the app.module.ts imports array contains no module on the legacy list — this catches an accidental re-registration during a merge.
  • A frontend equivalent: no file under the qualitative route tree may import from a legacy route or component directory.

Direction matters: legacy code may still reference shared foundations (BaseService, guards, Prisma), and that is fine. The rule is one-way — qualitative must not depend on legacy.

  • Advanced report templates: multiple donor formats driven by ReportTemplate.config; working schedules on the Phase 2 job runner.

Dependencies

Retention depends on the audio-deletion decision in §17. Withdrawal cascade depends on the complete evidence chain from Phase 2.

Risks

Withdrawal cascade is genuinely hard: deleting a participant's audio may orphan approved findings in already-delivered reports. Decide early whether withdrawal invalidates published findings or only prevents future use.

Acceptance criteria

  • A withdrawal request removes all in-scope data within the stated window and leaves an auditable tombstone.
  • Retention purge runs on schedule and is itself audited.
  • Per-org spend is reportable and enforceable against a cap.
  • Errors surface in a tracker with a trace id correlating client and server.

Explicitly not yet

No multi-region data residency, no on-premise deployment, no public API or SDK, no integration marketplace.

Conclusion

1. What can be reused safely?

Nothing can be reused as-is at the behaviour level — but the following are sound in shape and worth keeping: the design system and layout shell (~190 components, the largest single asset), API and database conventions (response envelope, DTO validation, UUID/soft-delete/tenant-column patterns), the Docker Compose stack (MinIO with an auto-created bucket, Redis and Mailpit are already running and merely unused by the code), Projects with its teams and activity timeline, Users and Organizations, the AuditLog and AiInference table shapes, the prompt registry, and the guided-workflow UX pattern from the study design workspace.

2. What must be rewritten?

Authentication (claims and expiry), tenancy enforcement (absent from every list and detail endpoint), authorization (guards unwired and permissions never seeded), media storage (local disk → durable object storage with resumable upload and signed URLs), the AI gateway (delete the fabricated fallback), report generation and export (hard-coded prose, and an export that returns JSON), guardrails (they reject ordinary transcript text), and audit wiring. Everything in the interview pipeline — guides, consent, interviews, recordings, transcription, transcripts, speakers, findings, quotations, review — is new construction.

3. What should be isolated as legacy?

Studies and the 8-step design workspace, logframes, indicators, questionnaires and the form builder, submissions, the sync engine, the Theory of Change builder, the quantitative dashboard metrics, the nine AI specialist agents, and the ~20 directories of aspirational planning documentation. Isolate by deregistration, not relocation: remove them from navigation and from the app.module.ts imports array, mark them legacy in a dated LEGACY.md inventory, and enforce the boundary with an import test in CI — leaving every file where it is and the schema untouched until the data-preservation decision is confirmed. Extract the versioning, publish/clone and translation patterns from questionnaires before the boundary closes.

4. What should be removed later?

After the data-preservation decision is made and dated: the nine specialist agents and their endpoints, the sync module, the questionnaire and indicator subsystems and their tables, the Laravel-era .env.example, the mobile/ Flutter documentation (retain only the offline and sync design notes as requirements), and the mock adapter once real integration tests replace its demo role.

5. What are the first ten implementation tasks?

  1. Fix the JWT issuer/audience mismatch and the parseInt('7d') expiry; add a sign→verify round-trip test. Nothing else can be validated until this works.
  2. Rebuild the bcrypt native binding and get the existing test suite executing, so there is a place to put regression tests.
  3. Generate and commit a baseline Prisma migration from the current schema, before any new models are added.
  4. Add a /health endpoint — Compose, CI and deploy all already expect one.
  5. Apply TenantGuard globally, derive organizationId from the token, and introduce a tenant-scoped base repository; add an integration test proving org A cannot read org B.
  6. Define and seed the permission catalogue, attach it to the six target roles, then decorate routes and enable PermissionGuard — in that order.
  7. Delete generateSimulatedResponse from the AI gateway and let provider failures propagate.
  8. Compile the mock adapter out of non-development builds and add a contract test that every client-declared endpoint exists on the server.
  9. Strip MERL entries from the sidebar and remove legacy modules from the app.module.ts imports array — without moving any file or touching the schema — then add the import-boundary test and confirm both that it passes and that it fails when a deliberate legacy import is introduced.
  10. Write the storage service against the already-installed AWS SDK and already-running MinIO, and migrate media upload off the local filesystem.

Tasks 1–4 are each under a day. Tasks 5–10 are the substance of Phase 1. Note that no interview feature appears in this list — that is deliberate.

6. What is the smallest credible qualitative interview MVP?

One project, one published interview guide, one assigned interviewer, one consented participant. The interviewer installs the PWA, goes fully offline, captures consent, records a 60-minute interview, and closes the browser. On reconnection the audio uploads resumably and exactly once, transcribes with speaker diarization, and a researcher corrects the text, reassigns a speaker, and approves the transcript. AI proposes findings from that approved transcript, each carrying a quotation that plays the matching audio. The researcher approves three, rejects one, and downloads a report containing only the approved three. Every step is visible in the audit log. That single trace — and nothing beyond it — is the MVP.

7. What should not be built yet?

Themes, codebooks, cross-interview analysis, contradiction detection, saturation tracking, inter-coder agreement, RAG retrieval, and translation workflows all wait for Phase 3 — they need a corpus of approved transcripts that does not yet exist. Retention automation, consent withdrawal cascade, PII redaction, DSAR endpoints, SSO/MFA, observability and multiple report templates wait for Phase 4. A native mobile app, video interviews, live transcription and unreviewed AI findings should not be built at all. And critically: no interview feature of any kind should be built until Phase 1 is complete — collecting real participant audio on a platform with broken authentication, no tenant isolation, no migrations and ephemeral storage would not be a prototype, it would be a data-protection incident.
